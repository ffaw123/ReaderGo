# 项目详细梳理

## 1. 视频处理暂停流程

```text
用户点击暂停（暂时还未实现分片上传时的断点续传）
→ API 写入 videos.status = paused
→ Worker 中的 withLifecycleMonitor 监测发现视频任务暂停
→ 设置 pauseRequested=true，调用 processorCtx 的 cancel()
→ Processor 感知 processorCtx.Err()，即任务取消，并退出
→ Worker 确认取消原因是暂停
→ returnJobToPendingAfterPause 改回任务状态为 pending
```

整个暂停流程依赖 Go 标准库的 `context` 实现。完整的 Context 链如下：

```text
worker/main.go:65
context.Background() 定义根 ctx
        │
        ▼
consumer.go:56
connectionCtx, cancel := context.WithCancel(ctx) 定义 RabbitMQ connectionCtx
        │
        ▼
worker.go:56
processorCtx, ... := x.withLifecycleMonitor(ctx, job) 定义每条任务独立的 processorCtx
        │
        ▼
对应的 Processor.Process(processorCtx)
```

## 2. 视频处理过程失败处理（Worker 内部消费失败时的处理）

| 错误类型 | 任务级重试 | 任务状态 | 视频状态 | DLQ |
| --- | ---: | --- | --- | ---: |
| 用户输入问题 | 否 | `failed` | `failed` | 否 |
| 永久处理错误 | 否 | `failed` | `failed` | 是 |
| OpenAI 永久 HTTP 错误 | 否 | `failed` | `failed` | 是 |
| 普通临时错误，次数未耗尽 | 是 | `pending` | 保持处理中 | 否 |
| 普通临时错误，次数已耗尽 | 否 | `failed` | `failed` | 是 |
| 视频正在暂停 | 否且不算失败 | `pending` | `paused` | 否 |

### 2.1 错误类型说明

1. **用户输入问题**

   Processor 使用 `userInputProcessError` 标记由视频内容本身导致、重复执行也无法改善的问题，例如视频中没有识别到有效语音或画面文字。该错误不会进行任务级重试，也不会进入 DLQ；任务和视频会标记为 `failed`，具体原因写入 `error_message` 并由前端展示给用户。

2. **永久处理错误**

   Processor 使用 `permanentProcessError` 标记模型配置或处理结果违反系统契约的问题，例如 Embedding 向量不是 1024 维，或者 Summary 连续三次返回无效结构。这类问题需要修改配置、模型或代码，重复执行当前任务无法恢复，因此任务立即标记为 `failed` 并进入 DLQ，不消耗任务级重试次数。

3. **OpenAI 永久 HTTP 错误**

   模型接口返回 `400`、`401`、`403`、`404` 或 `422` 时，通常表示请求参数无效、API Key 无效或无权限、模型不存在等问题。Worker 将其视为不可恢复错误，不进行任务级重试，直接将任务标记为 `failed` 并送入 DLQ。

4. **普通临时错误**

   未被标记为上述类型的错误默认视为可重试错误，例如网络连接失败、请求超时、HTTP `408`、`409`、`429`、`5xx`，以及暂时性的数据库、对象存储或 FFmpeg 错误。只要当前 `attempt` 小于最大次数，Worker 就会将任务改回 `pending`，增加 `attempt`，并通过 Outbox 延迟重新投递。

5. **重试次数耗尽**

   这不是独立的错误类型，而是普通临时错误已经达到最大任务执行次数后的结果。默认最多执行 4 个 attempt，重试间隔依次为 30 秒、5 分钟和 30 分钟；最后一次仍失败时，任务和视频标记为 `failed`，并进入 DLQ。

6. **视频正在暂停**

   这也不是处理错误。若 Processor 返回错误时视频已经是 `paused`，暂停状态优先：任务从 `running` 恢复为 `pending`，不增加 `attempt`，不进入 DLQ，等待用户恢复后重新投递。

## 3. RabbitMQ 流程梳理（整个 Worker 崩溃时通过租约机制保证容错性）

### 3.1 后续消息是在前置任务成功后产生

ASR 和 OCR 中任意一个完成时，都会检查二者是否都为 `succeeded`，代码位于 [internal/worker/worker.go（第 328 行）](E:/0MyCodeRepo/ReaderGo/internal/worker/worker.go:328)。

- 第一个完成：不创建 RAG 任务。
- 第二个完成：发现成功数量为 2，创建 `rag_index`。
- `rag_index` 成功后：同时创建 `embedding` 和 `summary`。

但并不是消费者直接调用 RabbitMQ 发布。实际过程如下：

```text
Processor 处理成功
→ ProcessingJob 改为 succeeded
→ 创建后续 ProcessingJob
→ 在同一数据库事务中写入 Outbox
→ Outbox Dispatcher 发布到 RabbitMQ
```

代码位于 [internal/worker/worker.go（第 217 行）](E:/0MyCodeRepo/ReaderGo/internal/worker/worker.go:217)。

### 3.2 任意 Worker 都可以从队列中发现消息并处理，但必须是对应类型的消费者

以 `video.asr` 消息为例：

- 可以由 Worker 1 的 ASR 消费者处理。
- 可以由 Worker 2 的 ASR 消费者处理。
- 不能交给 Summary 消费者处理，因为 RoutingKey 和队列不同。

Worker 不依赖进程内保存的上一步状态，处理结果都存放在 PostgreSQL 或 MinIO 中，因此换一个 Worker 继续处理没有问题。

### 3.3 保障消息隔离，防止不同用户、视频错乱的不只是 UserID 和 VideoID

消息实际包含以下字段，定义位于 [internal/queue/contracts.go（第 22 行）](E:/0MyCodeRepo/ReaderGo/internal/queue/contracts.go:22)：

```text
job_id
tenant_id
video_id
task_type
attempt
upload_method
```

各字段作用如下：

- `tenant_id`：租户隔离，防止跨用户访问。
- `video_id`：标识属于哪个视频的流水线。
- `job_id`：唯一定位某个具体任务。
- `task_type`：确认任务阶段。
- `attempt`：区分重试次数。
- `lease_owner`：防止多个 Worker 同时完成同一个任务。

领取任务时还会从数据库重新读取并验证这些字段是否匹配，代码位于 [internal/worker/worker.go（第 96 行）](E:/0MyCodeRepo/ReaderGo/internal/worker/worker.go:96)。

此外，数据库通过以下唯一索引保证一个视频不会重复创建同类型任务：

```text
(video_id, task_type)
```

索引定义位于 [migrations/001_init.sql（第 49 行）](E:/0MyCodeRepo/ReaderGo/migrations/001_init.sql:49)。

### 3.4 不能单纯相信 RabbitMQ 消息顺序

“后续消息正常情况下由前置任务成功后产生”是正确的，但系统不能假设队列里的消息永远严格有序，因为可能存在：

- Outbox 重复发布。
- RabbitMQ 重复投递。
- 消息重试和重新入队。
- 多 Worker 并发消费。
- 旧 `attempt` 消息延迟到达。

因此，真正保证流水线正确性的不是 RabbitMQ 顺序，而是：

```text
消息携带任务身份
+ PostgreSQL 保存真实状态
+ 前置任务状态检查
+ 行锁和唯一索引
+ attempt 校验
+ 租约
+ Worker 幂等处理
```

例如，即使一条 `rag_index` 消息异常提前出现，Worker 仍会检查 ASR 和 OCR 是否都成功，代码位于 [internal/worker/worker.go（第 302 行）](E:/0MyCodeRepo/ReaderGo/internal/worker/worker.go:302)。

所以更准确的表述是：任意 Worker 实例中的对应消费者都可以执行任务；RabbitMQ 负责分发通知，PostgreSQL 中的任务状态和约束负责保证多个用户、多个视频以及重复消息不会相互错乱。

## 4. 前端分片上传暂停与断点重传

### 4.1 为什么不将已上传分片保存在浏览器中，并通过其直接恢复？

上传会话设置了过期时间（1 天）。当用户暂停时间过长、超过期限时，会话失效，MinIO 已上传分片会被清空。如果通过浏览器保存的分片状态直接恢复，由于浏览器并不知道会话已经失效，后续仍会启动续传。并且暂停重传不是高频操作，没必要为少量性能收益增加更多不确定性。

### 4.2 恢复时会做什么？

```text
用户刷新页面后重新选择原文件
→ 前端重新计算文件指纹（未刷新页面时也会执行）
→ 校验文件名、大小、修改时间和指纹
→ 使用 localStorage 中的上传会话 ID 请求后端
→ 后端校验会话、租户和有效期
→ 后端调用 MinIO ListObjectParts
→ 返回实际已上传分片
→ 前端计算缺失分片
→ 为缺失分片重新申请预签名 URL
→ 只上传缺失分片
→ 后端再次查询 MinIO 并校验完整性
→ 合并分片，进入视频处理流水线
```

轻量 SHA-256 结构如下：

```text
SHA-256("readergo-v1:{文件大小}:" + 文件开头 64 KiB + 文件末尾 64 KiB)
```

小文件的处理方式如下：

- 不超过 64 KiB：实际计算整个文件。
- 64～128 KiB：同样计算整个文件。
- 大于 128 KiB：只计算开头和末尾各 64 KiB。

## 5. 同视频重复上传限制

### 5.1 上传流程

1. 前端在 Web Worker 中分块计算完整视频的 SHA-256。

2. 前端调用 `POST /api/uploads`，提交文件信息和 `content_sha256`。

3. 后端按以下顺序检查重复：

   ```text
   Redis → 未命中或故障 → PostgreSQL
   ```

4. 如果 Redis 或数据库命中同一用户的有效视频，则返回：

   ```json
   {
     "code": "UPLOAD_DUPLICATE",
     "video_id": "已有视频ID"
   }
   ```

   前端停止上传，读取并打开已有视频。

5. 如果没有重复：

   - 插入状态为 `uploading` 的视频记录。
   - 数据库唯一索引负责拦截并发重复上传。
   - 创建 MinIO Multipart Upload。
   - 插入 `upload_sessions` 记录。
   - 返回分片上传地址。
   - 将去重记录写入 Redis。

6. 浏览器直接把分片上传到 MinIO。

7. 全部分片完成后调用完成接口，后端：

   - 合并 MinIO 分片。
   - 将上传会话改为 `completed`。
   - 将视频改为 `processing`。
   - 创建处理任务和 Outbox 消息。

8. 如果上传被取消、过期或者视频最终处理失败，会删除对应 Redis 缓存，使相同文件可以重新上传。

### 5.2 Redis 的 key 和 value

默认 key：

```text
readergo:upload-dedup:v1:{tenant_id}:{sha256}
```

例如：

```text
readergo:upload-dedup:v1:6184f33c-...:9f86d081884c...
```

value：

```json
{
  "video_id": "60551b2b-b39f-48e7-8286-9ec43b7832ef"
}
```

默认有效期是 15 分钟。

这样设计的原因：

- `readergo`：区分应用和环境，可通过配置修改。
- `upload-dedup`：区分业务模块。
- `v1`：以后修改缓存结构时可以升级版本。
- `tenant_id`：只在同一用户范围内判断重复，避免跨用户泄露视频是否存在。
- `sha256`：稳定表示视频内容，Redis 平均可以在 `O(1)` 时间内查找。
- `video_id`：命中后可以告诉前端具体是哪条视频，并直接打开。
- 不缓存完整视频信息：避免视频状态变化后产生大量陈旧数据。
- 15 分钟 TTL：主要拦截短时间高频重复上传；缓存过期后仍会回源数据库判断。

## 6. 上传限流策略

### 6.1 一次上传时的令牌桶限流过程

令牌不是通过后台定时器主动补充的，而是在每次上传请求到达时“惰性计算”应该补充多少枚。且使用 Lua 脚本处理令牌业务确保原子性。

Redis 中保存两个字段：

```text
tokens          当前剩余令牌
last_refill_ms  上次补充令牌的基准时间
```

完整过程如下：

```text
上传请求到达
→ Redis TIME 获取当前时间
→ 计算距离上次补充经过了几个完整的 90 秒
→ 补充令牌，最多补到 5
→ 尝试消费 1 枚
→ 写回 tokens 和 last_refill_ms
→ 刷新 15 分钟 TTL
```

### 6.2 令牌桶的作用

当前令牌桶可以保证：

- 一个用户最多瞬间创建 5 个上传任务。
- 5 枚令牌耗尽后，新上传请求会被拒绝。
- 此后每 90 秒只恢复一次创建上传的机会。
- 多个 API 实例并发处理请求时，也不会超发令牌。
- 防止脚本在短时间内大量创建 `videos`、`upload_sessions`、MinIO Multipart Upload 和后台任务。

其效果是：

```text
最初：允许连续上传 5 次
第 6 次：返回 429
90 秒后：允许 1 次
再次耗尽：继续等待下一轮 90 秒
```

因此它同时提供：

```text
突发容量：5
持续节流：每 90 秒 1 次
```

## 7. 按时间区间画面理解的 Agent Loop

### 7.1 主 agent

当前请求输入：

```go
type OrchestratorInput struct {
	Question            string            "原始 Question"
	RewrittenQuery      string            "完成指代消解的 RewrittenQuery"
	AllowedRange        Range             "当前授权区间 AllowedRange"
	ProtocolInstruction string            "协议纠错或预算耗尽时的本轮控制指令"
	ForceFinal          bool              "是否关闭工具并强制生成最终回答，仅在服务端使用"
	RetrievalWindows    []RetrievalWindow "当前授权区间对应的 RAG 检索文本"
}
```

跨请求记忆不再放入 `OrchestratorInput`。画面 Agent 独立接收当前会话最近三轮完整 `user/assistant` 对话，并把它们按时间正序放在当前请求消息之前。历史不按回答模式过滤，因此普通对话、Summary、RAG、预设回答和画面理解回答都可用于承接上下文。开启画面理解时，用户消息落库正文会附加服务端生成的 `MM:SS-MM:SS` 时间范围；如果本轮确认了新的允许区间，回答完成时会在同一事务中把正文和 `vision` 元数据更新为最终范围，同时以 `requested_vision` 保留初始请求快照用于幂等校验。

本轮 Agent Loop 的 `assistant(tool_call)` 与 `tool` 结果继续放在当前请求之后。

主 Agent 有两种输出：

- 需要检查或继续补充画面证据时，通过原生 `tool_call` 调用 `inspect_video_range(start_ms, end_ms, interval_ms)`；首轮不强制调用工具。
- 可以结束时，返回包含 `action`、`evidence_status` 和 `answer` 的 `FINAL` JSON。`evidence_status` 为 `GROUNDED` 或 `NO_EVIDENCE`，且没有本轮成功视觉观察时不能返回 `GROUNDED`。

工具调用遵循以下原则：

- 已有观察足以回答时直接生成 `FINAL`，不重复抽帧。
- 相邻采样帧之间可能遗漏快速动作或关键变化时，通常缩小可疑时间范围并减小 `interval_ms`，提高时间分辨率。
- 需要检查当前授权区间内尚未覆盖的其他时间段时，应移动 `start_ms` 和 `end_ms`；此时 `interval_ms` 根据所需细节决定，不要求一定比上一次更小。
- 需要检查授权区间之外的明确时间范围时，主 Agent 可以先按目标范围输出 `inspect_video_range`。后端会在抽帧前中断该工具调用并请求用户确认，用户同意后更新授权范围，再继续执行同一个工具调用。
- 每次调用都要考虑剩余工具次数和帧预算；继续检查不能带来有效信息或预算已经耗尽时，生成 `FINAL`，证据不足则返回 `NO_EVIDENCE`。

因此，减小 `interval_ms` 是“细化同一动作过程”的主要方式，但不是所有后续工具调用的固定规则。服务端仍会将间隔限制在 `500～10000ms`，并根据区间长度校正采样帧数。

### 7.2 视觉观察模型

输入：

- 当前问题或完成指代消解后的问题（RewrittenQuery）；
- 本次工具调用实际抽取的连续视频帧；
- 实际采样间隔 `interval_ms`，用于确定帧序列的播放速率。

视觉观察模型不接收对话历史、RAG 文本、工具预算或 Agent 状态。

输出为一段简短的纯文本画面观察，只描述问题相关且直接可见的内容。它不规划下一步、不调用工具，也不生成面向用户的最终回答；观察结果会作为 `tool` 消息返回主 Agent。
